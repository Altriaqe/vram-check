## ADR-001 用 Rust 实现

**状态**：已采纳 · 2026-11-14

**背景**：三条硬约束里最狠的是体积 ≤2MB。候选方案的实测/估算体积：

| 方案 | 体积 |
|---|---|
| Python + PyInstaller | 60–120 MB |
| C# .NET 自包含 | 40–70 MB |
| Go + walk | 7–9 MB |
| egui | 4–6 MB |
| **Rust + Win32 原生** | **0.6–1.5 MB** |

**决策**：Rust。

**理由**：唯一能同时满足"≤2MB"和"不动辄需要运行时"的语言，且 Win32 绑定成熟（`windows` crate）。

**后果**：
- 开发速度慢于 Go/Python，尤其 UI 部分；
- 团队需要安装 MSVC 工具链（约 3 GB）；
- 换来的是体积、启动速度、内存占用三项全赢。

**替代方案**：Go + walk（8MB，超预算 4 倍）；C++（能更小，但开发效率太低）。

## ADR-002 用 Win32 原生控件，不用 egui

**状态**：已采纳 · 2026-11-14

**背景**：Rust 生态最省事的 GUI 是 `egui`/`eframe`。但它走 OpenGL（`glow`）。

**决策**：用 `windows` crate 直接调 Win32 原生控件（`SysListView32` + GDI）。

**理由**（按重要性）：
1. **远程桌面**：egui 需要 OpenGL 3.3，**RDP 下经常不可用或极慢**。而本机装了 ToDesk / 向日葵 / GameViewer 四个虚拟显卡，说明"远程串流"就是真实使用场景。
2. **老机器**：GDI 不需要任何 GPU，集显、虚拟机 WARP 都能跑。
3. **中文**：egui 默认字体无 CJK，要么内嵌（+5~10MB，直接超预算），要么运行期解析 `msyh.ttc`（TTC 解析有坑）。Win32 直接 `CreateFontW("Microsoft YaHei")`，**零成本**。
4. **体积**：4–6MB vs 0.6–1.5MB。
5. **启动**：150–300ms vs <100ms。

**后果**：
- 界面默认观感偏旧，需要用 owner-draw 做行内颜色和图标来弥补；
- ListView 的排序、多选、键盘导航要自己写，约 800 行。

**替代方案**：`native-windows-gui`（同一套控件，封装更好写），作为开发超期时的退路。

## ADR-003 基座选 hypomnesis，精准移植而非整包依赖

**状态**：已采纳 · 2026-11-14

**背景**：数据层（PDH 每进程显存）是最容易踩坑的部分。有两个开源参考：

| | gputaskman | hypomnesis |
|---|---|---|
| 语言 | Python | **Rust** |
| 许可证 | **未确认** | **MIT OR Apache-2.0** |
| 形态 | TUI 应用 | **库 + CLI** |

**决策**：
- gputaskman 只作**产品参考**，**不碰代码**（许可证未确认）；
- hypomnesis 作为**技术基座**，但**只移植 `pdh.rs` / `dxgi.rs` 的纯逻辑**，不做整包依赖。

**理由**：
1. 整包依赖拿不到我们要的口径（见 ADR-004），而它对外只暴露 `used_bytes`（Dedicated）；
2. 它的默认 feature 里有 `nvml`(libloading)、`metal`、`cli`(clap/ctrlc)、`nvidia-smi` 子进程——**每一样都是体积或"不占进程"的敌人**；
3. 裁剪后从 ~8000 行降到 ~900 行，接触面小、可控。

**后果**：
- 需要自己承担"上游漂移"的维护成本 → 用 `VENDOR.md` 锁 commit、季度 diff 缓解；
- **最终目标是回馈上游**（把 Local 口径提 PR），合并后即可切回依赖，摆脱 fork。

**替代方案**：整包依赖（被口径卡死）；完全自研（重复踩 10 个坑）。

## ADR-004 口径用 `Local Usage`，不用 `Dedicated Usage`

**状态**：已采纳 · 2026-11-14 · **本机实测支撑**

**背景**：同一时刻，两种口径算出的"进程合计"：

| 口径 | 合计 | 占整卡 718 MiB |
|---|---|---|
| `Dedicated Usage` | 923 MiB | **128.5%** |
| `Local Usage` | 675 MiB | **93.9%** |

交叉验证：PDH 整卡 718 MiB vs `nvidia-smi` 713 MiB（差 0.7%）。

**决策**：主界面用 `Local Usage`；`Dedicated` 只在"技术详情"里出现，标注"任务管理器口径"。

**理由**：
- 128.5% 是不可能的结果——`Dedicated` 把跨进程共享的 surface 重复计入了（同一块桌面画面可能同时算在应用、`csrss.exe`、`dwm.exe` 头上）；
- 用户一旦发现"加起来比显存还大"，第一反应就是软件在瞎报，信任瞬间归零；
- `Local` 的 93.9% 是可解释的：剩下 6% 是驱动/内核/无法归因的部分，正好对应界面上"未归属"那一行。

**后果**：
- **和任务管理器对不上**（TM 显示 Dedicated）。这是必须主动解释的事（PRD F-33），否则用户会认为我们算错了；
- 上游 hypomnesis 用的是 Dedicated，移植时必须改。

**替代方案**：跟随任务管理器用 Dedicated（数字对得上，但求和不自洽）；两个都显示（信息过载，违背"易懂"）。

## ADR-005 默认不常驻，放弃全局热键

**状态**：已采纳 · 2026-11-14

**背景**：全局热键要求进程常驻托盘，常驻就必然占内存、占句柄、可能出现在启动项里。

**决策**：默认关窗即退出。托盘与全局热键作为**可选**功能（P1），默认关闭。

**理由**：
- 用户明确要求"不占进程"；
- 这是一个**低频工具**——一天可能只用两次，没理由为它常驻一个 20MB 的进程；
- 用"启动快（<100ms）+ 记住上次状态"来补偿，体验损失很小。

**后果**：
- 无法做到"按一下就出来"；
- 需要保证冷启动足够快，否则补偿失败——**这是 ADR-001 选 Rust 的另一个理由**。

**替代方案**：常驻 + 热键（体验好，但违背硬约束）。

## ADR-006 界面收敛为三列表

**状态**：已采纳 · 2026-11-14

**背景**：v0.1–v0.2 设计过完整仪表盘：总览条 + 饼图 + 右侧详情面板 + "腾出 2GB"向导 + 历史曲线。

**决策**：收敛为 **程序 / 占用 / 描述** 三列，加一行总览、两个按钮。

**理由**：
- 实测 314 个进程里**只有 32 个持有显存**，不需要分页、不需要虚拟滚动；
- 用户的问题是"关哪个"，不是"给我一张图"；
- 页面越少，需要翻译的东西越少——**易懂的前提是少**；
- 向导三步的事，多选 + "关闭选中"一步就做完了。

**后果**：
- 看起来"简陋"，需要用文案质量来撑住价值；
- 历史曲线、悬浮窗降级到 P1/P2。

**替代方案**：完整仪表盘（信息密度高，但违背"易懂"，且撑大体积）。
